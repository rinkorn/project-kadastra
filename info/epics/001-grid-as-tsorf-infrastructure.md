# Эпик 001 — ЦОФ на сетке: сетка как инфраструктура расчёта ценообразующих факторов

**Статус:** Предложено
**Дата:** 2026-08-18
**Источник методологии:** [grid-rationale.md](../grid-rationale.md) (§1–§12)
**Связано:** [ADR-0010](../decisions/0010-methodology-compliance-roadmap.md) (roadmap), [ADR-0007](../decisions/0007-kazan-agglomeration-scope.md) (разрешения), [ADR-0024](../decisions/0024-road-network-advanced-features.md) (isochrone res=11), [hex-feature-layers.md](../hex-feature-layers.md) (три слоя)

## Цель

Сделать H3-сетку **единственным источником** ценообразующих факторов локации (Слой 1). ЦОФ считаются **один раз на ячейках**, хранятся в feature store по `h3_index`, а объект при сборке признаков **join'ится к ячейке** (с взвешиванием по доле перекрытия для крупных объектов). Это переводит пилот с «per-object расстояний» на полную методологию доклада.

## Зачем

ADR-0010 §1 фиксирует: «Используется ~5% методологии. Мы делаем per-object евклидовы расстояния, моно-площадные счётчики в одном радиусе и одну модель на класс». Блоки 1–4 roadmap закрыли **состав фич**, но оставили их **per-object**. Сетка как инфраструктура не реализована.

Что даёт перевод на сетку (из §2 доклада):

- **Репрезентативность** — распределение ЦОФ по всей территории (а не только по точкам объектов) → проверка совпадения распределений выборки и генеральной совокупности (§2 п.5).
- **Переиспользование** — ЦОФ считаются один раз, объекты только забирают.
- **Детерминизм** — группировка задаётся сеткой, а не объектом.
- **Независимые треки** — расчёт ЦОФ на сетке и оценка объектов распараллеливаются (§2 п.1).
- **Фундамент для темпоральных срезов** — значения ячейки можно хранить по годам (§10, блокируется треком 1).

## Текущее состояние — два пайплайна, и они не связаны

В коде два пути фич, и модель использует только один из них:

| Путь | Что делает | Ключ | Статус |
| --- | --- | --- | --- |
| **Сетка (Слой 1)** | `build_region_coverage` строит покрытие H3; `build_metro_features` / `build_buildings_features` / `build_road_features` считают фичи по ячейке; `build_gold_features` джойнит их в hex-gold | `h3_index` | **Legacy/retired.** Питал старую hex-модель (`train_valuation_model`, synthetic target) и эндпоинт `/api/hex_features`; после перехода на per-object пайплайн не пересобирался и отключён (см. `api/routes.py`). |
| **Объект** | `build_object_features` считает **все** ЦОФ локации per-object (`object_metro/road/neighbor/zonal/polygon/geom_distance/municipality_features`) + относительные | `object_id` | **Канонический.** Это вход моделей квартета, карты и инспектора. |

Разрыв: модель получает ЦОФ локации из **объектного** пути, где они пересчитываются для каждого объекта заново; **сеточный** путь (Слой 1) существует как наследие, но не подключён к объектам.

## Границы

**В скоупе:**

- ЦОФ **локации** (дистанционные, зональные доли/плотности, дорожная плотность, метро) → на сетку.
- Объект join'ится к ячейке; взвешивание по доле перекрытия для крупных объектов.
- Feature store ЦОФ по `h3_index` + читатель.
- Репрезентативность по всей территории.

**Вне скоупа (не трогаем):**

- **Собственные фичи объекта** (площадь, этажность, год, материал, геометрия полигона, возраст) — по определению объектные, на сетке их нет.
- **Относительные ЦОФ** (ADR-0012) — остаются как есть; перенос на полное распределение сетки — отдельный подэтап.
- Квартет моделей (ADR-0016), NSPD-источник, per-class модели — без изменений.
- **Темпоральные срезы** — блокируются треком 1 (сделки), фиксируются как отдельный будущий этап.

## Принятые решения

- **Разрешение ЦОФ-сетки — res 10 (≈75 м), res 11 опционально.** Res 10/11 уже есть в проекте ([ADR-0007](../decisions/0007-kazan-agglomeration-scope.md): `h3_resolutions = [7, 8, 9, 10, 11]`; res=10 — дефолт карты и object-CV, res=11 — isochrone-кэш [ADR-0024](../decisions/0024-road-network-advanced-features.md)). Методология — ~100 м; res 10 ≈ 75 м — ближайший H3-уровень, погрешность присвоения локации точечному объекту ≤ ~40 м, пренебрежимо для дистанционных/зональных ЦОФ. Отдельной «калибровки» под точные 100 м не делаем.

## Этапы

Темп — один этап ≈ один ADR + одна feature-ветка (ADR-0010 §3).

| # | Этап | Что делаем | Deliverable | Deps |
| --- | --- | --- | --- | --- |
| 1 | **Сетка опорных ячеек ЦОФ** | Разрешение фиксировано: res 10 (res 11 опционально). Зоны разрежения внутри/вне НП (§7.1); построить покрытие с тегом зоны | `tsorf_grid` coverage `(h3_index, resolution, zone)` | — |
| 2 | **ЦОФ на ячейках** | Переприцелить расчёт локационных ЦОФ с координат объекта на опорную точку ячейки: `dist_to_X`, `X_share`, `X_within`/`count_X`, `road_length`, `metro` | feature store ЦОФ по `h3_index` (Слой 1 полный) | 1 |
| 3 | **Feature store + читатель** | Хранить ЦОФ по `(h3_index, resolution)` в silver; порт + читатель (переиспользовать `feature_store`/`parquet_feature_store`) | store/reader ЦОФ | 2 |
| 4 | **Объект → ячейка join** | Переписать `build_object_features`: локационные ЦОФ берутся join'ом по ячейке (взвешивание для крупных), собственные — как есть; замерить метрики против per-object baseline (A/B) | объектный gold без per-object ЦОФ | 3 |
| 5 | **Репрезентативность** | Распределение ЦОФ по всей сетке vs по обучающей выборке → метрика/отчёт | отчёт репрезентативности | 4 |

## Прогресс

| Семейство ЦОФ | Статус |
| --- | --- |
| Дистанционные (`dist_to_*_m`) | ✅ на сетке: `compute_cell_geom_distance_features` + `BuildCellGeomDistanceFeatures` + join за `cell_tsorf_enabled` |
| Поли-площадные (`*_share_{R}m`) | ✅ на сетке: `compute_cell_polygon_features` + `BuildCellPolygonFeatures` + join |
| Зональные / плотность (`*_within_{R}m`, `count_*`) | ✅ на сетке, **self-free** (`compute_cell_zonal_features` + `BuildCellZonalFeatures` + join) |
| Дорожная плотность (`road_length_500m`) | ⏳ не начато |
| Метро (`dist_metro_m` через road-graph) | ⏳ объектная версия — walking distance от точной точки объекта |
| A/B против per-object baseline | ⏳ требует сборки данных + обучения |
| Репрезентативность | ⏳ не начато |

## Риски и открытые вопросы

1. **Разрешение ЦОФ-сетки** — решено, см. «Принятые решения»: res 10 по умолчанию, res 11 опционально.
2. **Точность per-cell vs per-object.** Погрешность ≈ радиус ячейки; доклад оценивает в десятые доли %, но надо замерить на наших метриках (этап 4, A/B).
3. **Разрежение сетки.** Плотная внутри НП / разреженная на межселенке (§7.1). Делать сразу или отложить (сначала uniform-сетка)?
4. **Относительные ЦОФ.** Сейчас считаются по объектам в родителе (ADR-0012); на полном распределении сетки могли бы считаться по всем ячейкам. Отложено.
5. **Миграция без регрессии.** Держим старый per-object расчёт как baseline для A/B; переключаем объектный путь на join только после подтверждения метрик.
6. **Крупные объекты.** Взвешивание по доле перекрытия (§12) критично для landplot; закладываем в этап 4.

## Definition of Done (эпик)

- ЦОФ локации считаются на сетке и хранятся по `h3_index` (не per-object).
- `build_object_features` получает локационные ЦОФ join'ом по ячейке; собственные фичи — без изменений.
- Метрики не хуже per-object baseline (в пределах десятых % по MAPE/WAPE).
- Есть отчёт репрезентативности (распределение ЦОФ по всей территории vs выборка).
- Roadmap ADR-0010 дополнен блоком; каждый этап закрыт своим ADR + feature-веткой.
