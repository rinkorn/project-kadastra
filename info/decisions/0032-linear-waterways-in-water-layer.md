# ADR-0032: Линейные водотоки OSM в водном слое (буферизация waterway=* в полигоны)

**Статус:** Accepted (код; пересборка реального слоя — follow-up)
**Дата:** 2026-08-21
**Контекст:** [ADR-0014](0014-poly-area-buffer-features.md) (доли полигонов в буфере), [ADR-0019](0019-poi-distances-and-zonal-counts.md) (дистанции до геометрий), [ADR-0030](0030-road-graph-water-components-bbox-fix.md) (водный фильтр road-графа)

## Контекст

Водный слой `data/raw/osm/kazan-agg-water.geojsonseq` собирался только из полигонов OSM (`natural=water`, `waterway=riverbank`, `landuse=reservoir`). Но большинство внутригородских рек, проток и каналов размечены в OSM линейными осями `waterway=river|stream|canal|ditch|drain` без полигональной геометрии. Последствия:

- речки не видны на карте;
- `dist_to_water_m` / `water_share_*` занижают воду рядом с линейными реками;
- водный фильтр дорожного графа (ADR-0030) не видит переправы через линейные реки.

## Решение

1. **Извлечение** (`scripts/extract_osm_polygons.py`): в фильтры слоя `water` добавлены `w/waterway=river|stream|canal|ditch|drain`. osmium export отдаёт их LineString-фичами в тот же `kazan-agg-water.geojsonseq`.
2. **Буферизация** (`kadastra/etl/water_linear_waterways.py`, пост-пасс в конце извлечения водного слоя): каждая линейная фича с `waterway` из этих классов заменяется полигоном-буфером; все прочие фичи (полигоны, точки-узлы) проходят без изменений.
   - Полу-ширина буфера: если тег `width` парсится в положительное число метров (`"10"`, `"10.5"`, `"10,5"`, `"6.5 m"`) — `width/2`; иначе дефолт по классу: river=10 м, canal=8 м, stream=3 м, ditch/drain=1.5 м. **Это приближение** (типовые ширины городских русел агломерации, смещённые в широкую сторону, чтобы фильтр графа с порогом 30 м из ADR-0030 не терял узкие речки), вынесено в константу `DEFAULT_HALF_WIDTHS_M`.
   - Класс вне таблицы дефолтов и без `width` (например `weir`) не буферизуется — остаётся линией (дистанционные фичи её видят, долевые — нет), вместо буфера с выдуманной шириной.
   - Буфер строится в UTM 39N (EPSG:32639, паттерн ADR-0014/ADR-0030), cap/join — round (естественно для русел), результат возвращается в WGS84.
   - Буферизованные фичи помечаются `source=osm_waterway_line_buffer` (паттерн provenance-маркера как у ESA-аугмента `source=esa_*`), исходные OSM-теги сохраняются.
3. **Точка интеграции — единый слой**, а не отдельный файл: все потребители (`load_geojsonseq_geometries`, карта, водный фильтр графа) геометрически агностичны и делают `unary_union` по списку геометрий — дописанные полигоны подхватываются без изменений в потребителях. ESA-аугмент (`build_esa_landcover_layer.py`) при перезапуске сохраняет наши фичи (стрипает только `esa_*`).

## Идемпотентность

Файл слоя на каждом прогоне пересоздаётся osmium export с нуля, пост-пасс буферизует линии ровно один раз. Пропуск существующего файла без `--force` — как раньше.

## Альтернативы

- **Отдельный файл `kazan-agg-water-lines.geojsonseq` + объединение на входе потребителей** — отвергнуто: трогать всех потребителей (карта, poly-area, geom-distance, water filter) ради разделения, которое ничего не даёт — downstream всё равно union'ит геометрии.
- **Дефолтные полу-ширины из гидрографических справочников / по тегу `intermittent` и др.** — отвергнуто как overkill: точность OSM-осей сама по себе ±метры, а потребители нечувствительны к ±50 % ширины (дистанции до кромки сдвигаются на единицы метров).

## Последствия

- **Пересборка реального слоя (follow-up):** `PYTHONPATH=src python scripts/extract_osm_polygons.py --layers water --force` (требует `data/raw/osm/volga-fed-district-latest.osm.pbf` и osmium-tool), затем при желании ESA-аугмент и пересчёт downstream (dist/share ЦОФ, водный фильтр графа → `edges.parquet`).
- Полигональные фичи `natural=water` / `riverbank` / `reservoir` не меняются.
